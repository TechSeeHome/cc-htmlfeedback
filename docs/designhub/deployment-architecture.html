Deploying the code vs. publishing a doc

Two completely separate operations share the word "publish" in everyday conversation. This is the mental model, grounded in what's actually running for cc‑htmlfeedback right now.

Once per version, or every publish? Deploying is only for code changes — roughly what you'd call "shipping a release." Publishing a doc with /publish‑design never deploys anything; it just writes a file + some spreadsheet rows that the already‑running deployment reads on the next request.
Single project, or a new one per doc? Single project, always. One Apps Script project serves every doc, from every repo, for the whole company. A doc is a row of data, not a piece of code — there is no per-doc project, deployment, or URL.

The two planes

Everything on script.google.com for DesignHub lives on one of two planes. They change on entirely different schedules.

Does this action need a deploy?

Publishing a doc

No deploy
  • Uploads the HTML/MD file to the data plane (Drive)
  • Creates/updates its comment sheet + catalog row
  • The already-running deployment serves it on the very next request — ?doc=<path> is just a lookup key
  • Anyone can do this any number of times a day; the script never notices

Changing bridge.js, widget.js…

Deploy required
  • New code only exists in your local checkout until pushed
  • clasp push updates the project; nothing live changes yet
  • A new version is a snapshot of that code
  • The deployment has to be told to point at it — that's the actual "go live" moment

What "publish a doc" actually does

  1. /publish-design runs locally

    Uploads your HTML/MD file into the DesignHub Drive folder for that repo + branch, via the Drive API — nothing touches script.google.com yet.

  2. Companion sheet + catalog row

    A comments spreadsheet is created (or reused, if you're republishing) and the catalog's index row is upserted.

  3. Someone opens the link

    The request hits the already-deployed web app's doGet(?doc=...), which resolves the path to that Drive file and serves it, live, with no code change involved.

What "deploy" actually does

  1. clasp push

    Uploads your local designhub/gas/*.js files into the script project. The project's code changes; nothing users hit changes yet — the live deployment is still pinned to the old version.

  2. clasp create-deployment -i <same id>

    Snapshots the current code as a new version, then re-points the existing deployment ID at it. The /exec URL never changes — every link anyone has already published keeps working.

  3. (if needed) rerun a trigger installer

    Only for changes to time-based triggers, like today's reconciler rename — a one-off manual step in the Apps Script editor, not part of every deploy.

The alternative — creating a new deployment instead of updating the existing one — would mint a brand-new URL and silently orphan every doc link already published. That's why every DesignHub code change reuses the same deployment ID.
