DesignHub:
publish, review, remember.

A hub on Google Workspace where design docs from our repos become shareable, rendered pages - reviewable by anyone with a TechSee Google account, PMs and management included, with in-page highlight-and-comment feedback (borrowed from cc-htmlfeedback) stored as structured data agents can act on. Module one of an org knowledge portal.

TechSee · platform design proposal · markdown version · builds on how cc-htmlfeedback works
01

The problem

Four gaps, one platform.

i

Design docs are invisible where they live

Agents and engineers produce rich HTML dashboards and MD plans inside repos - GitHub shows HTML as source code, and both need a GitHub seat to view. See PR #1 in this repo for a live example.

ii

Half the reviewers have no GitHub

PMs, CS, and management have Google accounts only. Today they get screenshots or nothing.

iii

cc-htmlfeedback is single-player

Highlight-to-comment with quote anchoring is exactly the right review interaction - but it is local-machine, anonymous, and its comments are disposable.

iv

Org knowledge is scattered

Docs, Slides, and Sheets full of knowledge exist all over Drive with no shared structure, taxonomy, or index.

02

Decisions so far

The log of what is already settled - challenge any of it in comments.

D1
Audience & identity
Eng (GitHub + Google), PMs/mgmt (Google only), AI agents as first-class actors.Feedback must work with only a Google login; agents read, write, and react to comments programmatically.
D2
Comment store
A Google Sheet per doc is the DB and source of truth.Rich ticket model (anchors, status, threads, author) that GitHub comment bodies would mangle; native to Workspace; PMs can literally open it; agents get it via one API.
D3
GitHub sync
Explicit Sync button, phase 2 - and it requires an open PR. Closed PR → "PR #N is closed, open a new one". No PR → "sync impossible".Deliberate batching, no notification spam, no artificial PRs. The sheet is the always-on store; GitHub is strictly the review-time mirror.
D4
Runtime
Approach C: pure Apps Script v1, designed to graduate to any host later.Zero infra, cost, and ops now; an evidence-based exit later - not a rewrite.
D5
Cloud independence
Hard rule: Google Workspace only - no cloud assumed.Drive works with any cloud. The future serving layer can be any host anywhere, talking Drive/Sheets over public REST APIs.
D6
Publishing
Claude Code skill on demand - /publish-design.Human- or agent-triggered, no per-repo config. A CI wrapper can come later against the same contract.
D7
V1 scope
Publish + view + tree · in-page comments → Sheet · agent access. PR sync deferred to phase 2.Removes all GitHub-write integration from v1.
D8
Portal trajectory
DesignHub is module 1 of an org knowledge portal; navigation is catalog-driven from day one.Existing Docs/Slides/Sheets register into the same catalog later - no redesign, no file moves.
03

Architecture: three layers

Click a layer to expand it. The rule that holds everything: all value lives in the bottom two layers under documented contracts; the top layer is disposable.

Publisherengineer or agent in any repo, any machinevia /publish-design → Drive API
Reviewereng · PM · management - anyone in the domainvia Google login → web app
AI agentreads docs, reads/writes/reacts to commentsvia Sheets/Drive REST API

Serving thin · disposable · Apps Script now

One standalone Apps Script web app: tree UI, doc serving with widget injection, MD rendering, and a comment bridge. Deleted tomorrow → zero data loss.

Deploy: "execute as me" (dedicated publisher account eventually), access "anyone in the domain". Identity for free: Session.getActiveUser().getEmail() - no OAuth prompts, no tokens in the browser.

Serving: ?doc=<path> reads the file from Drive, injects the adapted cc-htmlfeedback widget (same inject.js trick), returns via HtmlService. MD renders to HTML at view time, then gets the same widget - PMs comment on rendered Markdown exactly like on HTML.

Comments: widget → google.script.run bridge (no CORS, nothing to secure) → append row to the doc's Sheet. The bridge functions are deliberately REST-shaped: listCatalog · getDoc · submitComment · listComments · reply · setStatus - a future host on any cloud implements the same six calls.

Storage Drive files + comment Sheets

The published assets and their conversations. Physical tree: DesignHub/<repo>/<feature>/doc + a companion Sheet per doc as its comment DB.

Comment ticket schema (carried from cc-htmlfeedback, extended for multi-user): id · parentId (threading) · type comment|strike|reply · status open → in-progress → resolved|declined · the anchor triple quote/context/section · note · authorEmail/authorName · source web|agent · docVersion · result/files (agent outcomes) · timestamps.

Meta tab per doc: repo, path-in-repo, branch, commit SHA, PR#, jira, publisher, publish history.

Anti-lock-in discipline: no PropertiesService/CacheService as data stores, no Apps-Script-only formats.

Catalog _catalog Sheet · the portal backbone

One master registry: every knowledge asset is a row. Navigation reads the catalog, never folders. This is what the knowledge portal grows out of.

Row: id · type html|md (later + gdoc|gslides|gsheet|link) · title · repo · feature · jira · tags · owner · driveFileId · url · status active|archived · publishedAt · updatedAt.

V1: only the publish skill writes rows; the tree UI is a rendering of the catalog grouped by repo/feature.
Portal phase: existing Docs/Slides/Sheets register as rows pointing at their current files, opened in native viewers - same tree, search, and taxonomy across published designs and existing content. Bulk importer for whole folders.

Taxonomy lives in columns, not folder paths - browsing by team, epic, or product area later is just another view over the catalog. No file moves, no redesign.
📌 Riskiest assumption, tested first: a real design HTML (the CRM dashboard) served through HtmlService renders faithfully inside the iframe sandbox with the widget's comment round-trip working. Half-day spike - validates or kills the v1 runtime while switching is still free.

Runtime-agnostic by design - any future host inherits these unchanged.

05

Scope & roadmap

V1 · now

Publish & review

  • /publish-design skill: upload HTML/MD + metadata, upsert catalog, create comment Sheet, return link
  • Google-login-gated viewing; MD rendered, widget on everything
  • Tree UI over the catalog (repo/feature)
  • Comments → Sheet: identity, threads, statuses
  • Agent access = documented Sheet schema + REST how-to
Phase 2

Close the GitHub loop

  • Sync-to-PR button (open PR required - D3)
  • Eng as themselves; PMs via bot token + "on behalf of"
  • Quote → source-line mapping for inline review comments; plain comment fallback
  • Agent fix loop: read open tickets, apply fixes, re-publish
Phase 3

The knowledge portal

  • Register existing Docs/Slides/Sheets into the catalog (bulk importer)
  • Tags / team / epic navigation facets, search
  • Portal home replacing the v1 tree
  • One index over everything the org knows
06

Open questions

Unsettled - these are the highest-value places to comment.

Publish skill CLI shape/publish-design <file> [--feature X --jira Y] with repo/branch auto-detected from git? What defaults are right?
MD renderingClient-side (bundled marked.js, zero server work) vs server-side in Apps Script (cleaner output, more code)? Leaning client-side.
Re-publish semanticsOverwrite the Drive file (Drive keeps revisions) + bump catalog updatedAt? Flag old comments whose anchors were lost (cc-htmlfeedback has anchorLost for this)?
Permissions granularityOne shared folder visible to the whole domain, or per-repo subfolder ACLs? V1 assumption: whole-domain read.
Status lifecycleIs open → in-progress → resolved/declined right for mixed human + agent review, or do we need an acknowledged state?
Dedicated publisher accountA real service user (designhub@) as script owner from day one, or migrate later?
Naming convention<repo>/<feature-or-JIRA>/<basename> enough? Where do versions show - catalog only, or in the doc name?
