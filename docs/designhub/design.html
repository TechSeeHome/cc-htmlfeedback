DesignHub:
publish, review, remember.

A hub on Google Workspace where design docs from our repos become shareable, rendered pages - reviewable by anyone with a company Google account, PMs and management included, with in-page highlight-and-comment feedback (borrowed from cc-htmlfeedback) stored as structured data agents can act on. Module one of an org knowledge portal.

Platform design proposal · markdown version · builds on how cc-htmlfeedback works
01

The problem

Four gaps, one platform.

i

Design docs are invisible where they live

Agents and engineers produce rich HTML dashboards and MD plans inside repos - GitHub shows HTML as source code, and both need a GitHub seat to view. See PR #1 in this repo for a live example.

ii

Half the reviewers have no GitHub

PMs, CS, and management have Google accounts only. Today they get screenshots or nothing.

iii

cc-htmlfeedback is single-player

Highlight-to-comment with quote anchoring is exactly the right review interaction - but it is local-machine, anonymous, and its comments are disposable.

iv

Org knowledge is scattered

Docs, Slides, and Sheets full of knowledge exist all over Drive with no shared structure, taxonomy, or index.

02

Architecture: three layers

Click a layer to expand it. The rule that holds everything: all value lives in the bottom two layers under documented contracts; the top layer is disposable.

Publisherengineer or agent in any repo, any machinevia /publish-design → Drive API
Reviewereng · PM · management - anyone in the domainvia Google login → web app
AI agentreads docs, reads/writes/reacts to comments, renders docs locally for visual contextvia Sheets/Drive REST API - no web-app login needed

Three flows, one storage layer - the map before the clickable detail below.

Serving thin · disposable · Apps Script now

One standalone Apps Script web app: tree UI, doc serving with widget injection, MD rendering, and a comment bridge. Deleted tomorrow → zero data loss.

Deploy: "execute as me" (dedicated publisher account eventually), access "anyone in the domain". Identity for free: Session.getActiveUser().getEmail() - no OAuth prompts, no tokens in the browser.

Serving: ?doc=<path> reads the file from Drive, injects the adapted cc-htmlfeedback widget (same inject.js trick), returns via HtmlService. MD renders to HTML at view time (client-side, bundled renderer - D10), then gets the same widget - PMs comment on rendered Markdown exactly like on HTML. Injection also sets <base target="_top"> - HtmlService's IFRAME sandbox requires explicit link targets or in-doc links silently fail.

Comments: widget → google.script.run bridge (no CORS, no extra HTTP endpoints to run) → append row to the doc's Sheet. Doc scripts share the HtmlService page and can reach the bridge too - D17 defines the containment contract (comment-rows-only surface, server-side identity stamping, audit trail). The bridge functions are deliberately REST-shaped: listCatalog · getDoc · submitComment · listComments · reply · setStatus - a future host on any cloud implements the same six calls. Every mutating call carries the doc path, so the bridge resolves the target Sheet directly instead of scanning all Sheets for a comment UUID.

Agents - full context, no new infrastructure: (1) structured - comments via Sheets REST, each carrying the quote/context/section anchor triple that locates it in the doc text; (2) source - the byte-exact doc via Drive REST; (3) visual - the agent renders the fetched doc in a local browser tool (dev-browser, Playwright) and locates the anchors on the rendered page before acting. No Google login needed: the file comes from the Drive API - agents never touch the web app. Read access = domain-wide sharing (D11); write access = Shared Drive membership (D18): agent identities join the DesignHub Shared Drive once as Contributor, so a CI bot or non-publisher developer writes as itself with no per-Sheet grants (D13's designhub-agents@ group is deferred until identity churn justifies it).

Storage Drive files + comment Sheets

The published assets and their conversations. Physical tree: DesignHub/<repo>/<feature>/doc + a companion Sheet per doc as its comment DB.

Comment ticket schema (carried from cc-htmlfeedback, extended for multi-user): id · parentId (threading) · type comment|strike|reply · status open → in-progress → resolved|declined|anchor-lost (auto-set on re-publish when the quote is gone - D15; an accepted strike auto-closes resolved instead) · the anchor triple quote/context/section · note · authorEmail/authorName · source web|agent · docVersion · result/files (agent outcomes) · timestamps.
open→ in-progress→ resolved declined anchor-lost

a strike ticket whose quote disappears on re-publish auto-closes straight to resolved - never anchor-lost (D15).


Meta tab per doc: repo, path-in-repo, branch, commit SHA, PR#, jira, publisher, publish history.

Anti-lock-in discipline: no PropertiesService/CacheService as data stores, no Apps-Script-only formats.

Catalog one _index Sheet per feature + derived rollup

One _index Sheet per feature folder (per repo/feature) - never shared, never org-wide. Writes stay sharded: each feature folder holds its own small _index Sheet (source of truth). Reads stay unified: a single org-wide _portal-index rollup is derived from all the shards as a disposable cache. Navigation reads indexes, never folders - folders are physical storage, and coupling browsing to them would mean moving files every time taxonomy changes (team, epic, product area).

Row (same in shards and rollup): id · type html|md (later + gdoc|gslides|gsheet|link) · title · repo · feature · jira · tags · owner · driveFileId · commentSheetId · url · status active|archived · publishedAt · updatedAt.

V1: the publish skill writes only its feature's _index (+ pokes the rollup refresh); the tree UI reads the _portal-index rollup grouped by repo/feature. Rollup rebuilds on publish + a periodic Apps Script trigger.
Portal phase: existing Docs/Slides/Sheets register as index rows pointing at their current files, opened in native viewers - same tree, search, and taxonomy across published designs and existing content. Bulk importer for whole folders.

Taxonomy lives in columns, not folder paths - browsing by team, epic, or product area later is just another view over the rollup. No file moves, no redesign.

Why shards + one derived rollup (not one master sheet, and not shards alone)? Sharding the writes keeps each index small, manageable as the org grows, ACL-able per repo/feature, with a tiny blast radius - while cross-repo search and the portal still need a single queryable surface, and per-shard scatter-gather on every tree load would be slow. The rollup gives that surface as a regenerable cache: writes stay clean and distributed, reads stay unified, and losing the rollup costs a rebuild, not data. Per-PR indexes were rejected outright: PRs are ephemeral, docs outlive them (see D3). Per-repo indexes were rejected too: a repo never expires, so one shared index would grow forever and put every concurrent feature's publish in write contention on the same Sheet - feature-scoped shards stay bounded, archivable with the feature, and cap a bad shard's blast radius at one feature instead of a repo's full history.
📌 Riskiest assumption, tested first: a real design HTML (the CRM dashboard) served through HtmlService renders faithfully inside the iframe sandbox with the widget's comment round-trip working. Half-day spike - validates or kills the v1 runtime while switching is still free.
03

Decisions so far

The log of what is already settled - challenge any of it in comments.

D1
Audience & identity
Eng (GitHub + Google), PMs/mgmt (Google only), AI agents as first-class actors.Feedback must work with only a Google login; agents read, write, and react to comments programmatically.
D2
Comment store
A Google Sheet per doc is the DB and source of truth.Rich ticket model (anchors, status, threads, author) that GitHub comment bodies would mangle; native to Workspace; PMs can literally open it; agents get it via one API.
D3
GitHub sync
Explicit Sync button, phase 2 - and it syncs into an open PR. Closed PR → "PR #N is closed - open a new one". No PR at all → explain there's nothing to sync to yet and offer to open a new PR for the doc.Deliberate batching, no notification spam, no unsolicited PRs - the platform guides you to a PR instead of refusing. The sheet is the always-on store; GitHub is strictly the review-time mirror.
D4
Runtime
Approach C: pure Apps Script v1, designed to graduate to any host later.Zero infra, cost, and ops now; an evidence-based exit later - not a rewrite.
D5
Cloud independence
Hard rule: Google Workspace only - no cloud assumed.Drive works with any cloud. The future serving layer can be any host anywhere, talking Drive/Sheets over public REST APIs.
D6
Publishing
Claude Code skill on demand - /publish-design.Human- or agent-triggered, no per-repo config. A CI wrapper can come later against the same contract.
D7
V1 scope
Publish + view + tree · in-page comments → Sheet · agent access. PR sync deferred to phase 2.Removes all GitHub-write integration from v1.
D8
Portal trajectory
DesignHub is module 1 of an org knowledge portal; navigation is catalog-driven from day one.Existing Docs/Slides/Sheets register into the same catalog later - no redesign, no file moves.
D9
Publish defaults
Skill infers repo/branch/feature/jira from git + session context, shows resolved values for user approval before publishing; anything unknown gets the explicit placeholder unassigned.No silent guessing - the publisher confirms; "unassigned" is greppable and can't be mistaken for a real value.
D10
MD rendering
Client-side for v1 (bundled renderer at view time, incl. mermaid support - design docs use mermaid blocks); revisit server-side only if output quality demands.Zero server work, one less moving part; easy to swap later.
D11
Permissions
Whole-domain read for v1 via one shared folder. Tightening folder ACLs is NOT supported until the serving-layer viewer check ships (same milestone) - the web app serves as the owner account, so a tightened folder would still be served to any domain user: a silent leak, not protection. V1 contract: publish only what the whole domain may read.Owner-serving bypasses Drive ACLs; pairing ACL support with the viewer-access check keeps the contract honest.
D12
Comment lifecycle
V1 ships open → in-progress → resolved/declined as-is; richer states are out of scope for v1. V2 candidates: sort comments by creation / update date.Don't overdesign the lifecycle before real usage; sorting emerged as a concrete v2 need.
D13
Accounts
Developers publish as themselves (own Google OAuth; owner = their email). Publish write access is a one-time setup grant: the designhub-publishers@ group holds editor (content-manager) rights on the DesignHub root, so any developer or CI identity in the group creates folders, uploads docs, and upserts _index shards with its own credentials. The web app script owner starts as a personal admin account, migrates to a dedicated designhub@ service user later. The publish skill grants editor access on the companion Sheet and feature _index to two writers: the serving account (reviewer comments go through the bridge as that account) and the designhub-agents@ Google group - any agent identity (CI bot, another developer's session) joins the group once and writes via Sheets REST as itself.Script owner only affects what account serves files and whose quota is used - never authorship. Whole-domain sharing (D11) is read-only: without the publishers group every non-owner's first Drive write would fail; without the agents group a non-publisher agent's writes would fail with Sheets permission errors.
D14
Naming
Filenames stay original and the repo-relative subpath is preserved under the feature folder (docs/api/design.md → <feature>/docs/api/design.md) - identical basenames never collide. The <feature> folder is a single sanitized path component: separators in branch names are encoded (feature/new-ui → feature--new-ui) so a slashed branch can't collide with a real subdirectory; the _index keeps the original string, and publishing into a folder whose _index records a different original feature fails loudly. No versions in filenames: version/date belong inside the doc content and in index metadata (updatedAt, Drive revisions).Renaming on publish breaks the repo ↔ Drive mapping; subpath mirroring is collision-proof only if the feature segment can't itself contain separators; Drive revisions + the index already track versions.
D15
Re-publish
The publish flow runs the re-anchor check on every non-terminal ticket (open and in-progress) using the full anchor triple (quote + context + section - a bare quote match at a different occurrence counts as lost). Quote gone → anchor-lost, a distinct terminal status clearly marked as not fixed, never confused with resolved - an in-progress ticket surfaces as lost instead of dangling anchorless forever. Exception - strike tickets: the quote disappearing IS the requested fix, so an accepted strike auto-closes as resolved, not anchor-lost.No manual triage burden in v1; the separate status keeps auto-closed feedback honest, filterable, and recoverable; the strike branch keeps accepted deletions from being misfiled as losses.
D16
Repo strategy
Monorepo in the fork, sync-safe: DesignHub lives in additive-only paths (designhub/, plugins/designhub/) and never edits upstream files (sole exception: a 5-line marketplace.json entry). The widget variant is generated by a fail-loud build transform from upstream's untouched feedback-widget.html. Sync = git merge upstream/main + rebuild + tests; fork-side CI checks every merge.Single widget source keeps UX improvements flowing to both products; additive paths make upstream merges conflict-free indefinitely; the one brittle joint fails loudly at build time. Long-term: offer the transport-adapter refactor upstream.
D17
Doc scripts vs the bridge
Published HTML runs its own scripts in the same HtmlService page as the widget, so doc code can call the privileged google.script.run bridge. V1 contains rather than isolates: the bridge surface is comment-Sheet-rows only (and must never grow broader capabilities); every mutating call stamps authorEmail server-side from Session.getActiveUser() - client-supplied identity is ignored; status changes append to the audit history; v1 publishers are trusted domain developers (D11). True isolation - doc content in a sandboxed iframe, widget bridging via postMessage - is a stated precondition for accepting content beyond trusted repos and for the serving-layer graduation.A sandboxed content frame breaks the widget's direct selection/anchoring model - too costly for v1. Capped blast radius + server-side attribution + audit keeps the worst case at "attributable comment noise from a doc a trusted colleague published".
D18
Storage root & v1 access grants
Shared Drive as the DesignHub root. V1 access = Shared Drive membership, not per-Sheet grants: publishers are Content managers, each agent identity is added once as Contributor, and the serving account is a Contributor too. The publish skill makes no permissions.create calls. D13's designhub-publishers@/designhub-agents@ groups are deferred - they become the membership targets (one group added to the drive instead of N users) only once identity churn justifies admin-managed groups; D13's authorship model (publish as yourself, agents write as themselves) is unchanged.An org-owned root survives offboarding and personal-quota entanglement; drive-level membership gives the join-once grant the groups were invented for, with zero Workspace-admin work for v1 and fewer moving parts in the publish flow.
D19
Rollup refresh mechanism
The publish skill upserts the _portal-index row directly via Sheets REST in the same flow as the feature-shard write (atomic values:append - concurrent publishes of distinct docs can't clobber each other); a periodic Apps Script trigger runs the reconciler: a full rebuild from _index shards, implemented as pure JS (node --test-able). No skill→web-app call exists at all. Reconciler interval: hourly to start.Validated in POC-5 against the real Shared Drive: idempotent upserts, parallel-publish safety, and clear-then-rebuild convergence all proven. The skill already holds Sheets creds and the exact row, while CLI→GAS-web-app auth is a project of its own - eliminating the call removes the whole problem; rebuild-from-shards keeps the rollup honest as a disposable cache.
04

The contracts

Runtime-agnostic by design - any future host inherits these unchanged.

DesignHub/                          (shared folder or Shared Drive)
  _portal-index                     (Sheet - derived rollup, disposable cache)
  <repo>/
    <feature-or-JIRA>/              e.g. PROJ-123-crm-evaluation
      _index                        (Sheet - this feature's docs, source of truth)
      dashboard.html                published doc, byte-exact source
      dashboard.html.comments       (Sheet - this doc's comment DB)

The companion Sheet is named after the full published filename (dashboard.html.comments vs dashboard.md.comments - .html/.md twins get distinct comment DBs), but the name is a human-browsing convention only: the _index row records the authoritative commentSheetId and all consumers resolve the Sheet by id, never by name.

bridge function (v1, google.script.run)future REST equivalent
listCatalog(filter)GET /catalog
getDoc(path)GET /docs/{path}
submitComment(path, ticket)POST /docs/{path}/comments
listComments(path)GET /docs/{path}/comments
reply(path, parentId, note)POST /docs/{path}/comments/{id}/replies
setStatus(path, id, status)PATCH /docs/{path}/comments/{id}

Every mutating call carries the doc path - with one companion Sheet per doc, the bridge resolves the target Sheet directly from the path (via the _index row's commentSheetId) instead of scanning every Sheet for a comment UUID (ambiguous the moment two docs exist).

05

Scope & roadmap

V1 · now

Publish & review

  • /publish-design skill: upload HTML/MD + metadata, upsert feature _index (+ rollup refresh), create comment Sheet, return link
  • Self-contained docs only: no asset route, so the skill scans for relative src/href refs and warns loudly (publish on explicit confirm); multi-file docs are phase 2
  • Google-login-gated viewing; MD rendered, widget on everything
  • Tree UI over the _portal-index rollup (repo/feature)
  • Comments → Sheet: identity, threads, statuses
  • Agent access = documented Sheet schema + REST how-to + local render recipe for visual context
Phase 2

Close the GitHub loop

  • Sync-to-PR button (open PR required - D3)
  • Eng as themselves; PMs via bot token + "on behalf of"
  • Quote → source-line mapping for inline review comments; plain comment fallback
  • Agent fix loop: read open tickets, apply fixes, re-publish
  • Richer comment lifecycle + sorting by creation / update date (D12 candidates)
  • Multi-file docs: publish relative assets + rewrite URLs - lifts the v1 self-contained-only contract
Phase 3

The knowledge portal

  • Register existing Docs/Slides/Sheets into the catalog (bulk importer)
  • Tags / team / epic navigation facets, search
  • Portal home replacing the v1 tree
  • One index over everything the org knows
