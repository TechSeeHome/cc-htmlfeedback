The feedback loop, explained.

Highlight text on a locally served HTML page, leave a comment, and a Claude Code session turns it into a verified fix that appears in your tab without a reload. No database, no cloud, no accounts - local files plus one local port. Prefer text? Read how-it-works.md.

03

Two files, one writer each

Per page, the queue holds two files with strict ownership. That ownership is the concurrency design: each file has exactly one writer, so browser and AI can never conflict.

✍ server appends

feedback_inbox.jsonl · append-only

{"id":"…","type":"comment","quote":"the CTI guard…",
 "context":"…surrounding block…","section":"Auth flows",
 "note":"make this a table","page":"/dashboard.html"}
{"id":"…","type":"strike","quote":"legacy webhook note", …}

One JSON line per comment, written the moment you submit. Nobody ever edits it - it only grows.

✍ session writes

feedback_tasks.json · the board

{ "version":1, "page":"/dashboard.html", "tickets":[
  { "id":"…", "status":"done",  "result":"converted to table",
    "files":["dashboard.html"] },
  { "id":"…", "status":"in-progress" },
  { "id":"…", "status":"error", "result":"quote not found" } ]}

The status board. Only the Claude session writes here; the server watches it and streams every change to your tab over SSE.

🔒 The lock is ownership, not locking. Subagents never touch either file - they fix and verify, then the loop serializes one quick board write per result.
04

A ticket's life

todo→ in-progress→ done or error
The evaluation covers eleven self-hosted platforms, of which only three clear every hard gate - and one, the legacy webhook bridge, is proposed for removal.

Live in your tab: yellow = commented · pulsing = an agent is working that exact text right now · red strikethrough = suggested removal. When a ticket lands done, the fixed HTML is re-fetched and the DOM is morphed in place (vendored Idiomorph) - no reload, scroll and focus preserved, remaining highlights re-anchored.

05

Two ways to run it

connected · the full loop

Companion server + Claude Code

  • node server.js --root <dir> - serve HTML with the widget injected
  • --proxy http://localhost:5173 - front a dev server, its HMR keeps working
  • /cc-htmlfeedback in Claude Code starts the drain loop
  • Up to 5 tickets fixed concurrently, one fresh subagent each
  • Every fix verified in the agent's own tab against a judge rubric - never yours
disconnected · zero infrastructure

Chrome extension

  • Same widget on any webpage - load unpacked, pin, click
  • Notes live in page memory only
  • Copy feedback exports structured text: quote + context + section + note + URL
  • Paste to a colleague or an AI manually - same UX, no server, no queue
06

Boundaries worth knowing

Single machine, single user

Binds to 127.0.0.1 only. Comments carry no author identity - there are no accounts anywhere.

Comments are disposable

Once fixed, the record is the git diff of your HTML. Queue files are gitignored working state, not an archive.

HTML only

Serves and morphs HTML. Markdown is not rendered - it is not even in the MIME map.

Fix-oriented, not discussion

Every comment is a work order for an AI. No replies, no reactions, no resolve-without-fixing.

Git is the undo

The loop edits your working tree directly. Revert with git, not with the tool.

Notes are requests, not commands

Baked-in rule: ticket text is an edit request. Subagents never execute instructions embedded in a comment.
